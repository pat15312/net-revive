# Dispatch, durability and recovery decisions

1. **Atomic admission.** A `BEGIN IMMEDIATE` transaction verifies setup, operator, group state, configured membership, site and all group/target reservations. It records the event and target snapshots and reserves every target before releasing the database transaction. Competing clients cannot both pass the same reservation checks.
2. **Trusted membership.** The restart endpoint accepts only an operator name and the group ID in its URL. Target site/device/port identity is loaded from the database and copied into the event. Configuration changes affecting hardware are refused while dispatch is in progress.
3. **Live preflight.** Every target is checked using the documented device details endpoint. Preflight completes for the group before commands are sent, reducing the chance that powering a controller or gateway interrupts validation of other targets. A validation failure is recorded, and other targets still proceed.
4. **Bounded concurrency.** At most four port operations run concurrently across the process. Different ports are independent API operations. This sends multi-port requests promptly without unbounded load on a small controller. It cannot guarantee all commands reach switches if an earlier restart severs their management path; configure groups accordingly and inspect partial results.
5. **No blind retry.** Each target's attempt is persisted before sending. Acceptance is recorded immediately after the API response. HTTP errors and transport failures are sanitized. A timeout or 5xx can mean acceptance is unknown. Retrying a POST could restart equipment a second time, so NetRevive does not retry it.
6. **Persistent cooldown.** Admission reserves the whole group even if dispatch lasts longer than its normal cooldown. Completion releases in-flight reservations but extends persisted cooldown deadlines from that time. Explicit failures and unknown outcomes retain cooldown too, conservatively preventing rapid repeats. Non-overlapping groups remain independent.
7. **Crash reconciliation.** One process owns the database, enforced with a file lock. Startup marks abandoned dispatches interrupted, preserves known per-target results, records unknown or unattempted remaining results and starts a fresh cooldown. It does not replay commands. Unexpected worker exceptions use the same reconciliation for the affected event only. Graceful shutdown gives existing work time to finish; unfinished work remains reconcilable.
8. **Recovery is separate from acceptance.** Network monitoring begins only after dispatch has completed with at least one confirmed accepted target. A partial operation stays partial even if network health recovers. None mode never reports recovery. Consecutive checks use distinct post-dispatch samples, reset on failure, and cannot bridge a server restart. Timeouts use a deadline captured at admission, so later settings edits do not rewrite existing events.
9. **Immutable history.** Target snapshots contain site, switch identity/name, port identity/number/name, labels and enabled/capability state. The group snapshot includes its original button and settings. Only operational result and recovery fields are updated after admission. Configuration and operator changes do not rewrite snapshots.
10. **Clock and storage.** UTC Unix timestamps are authoritative; the browser renders them with the selected IANA timezone, including DST. A reasonably correct host clock and durable local SQLite storage are required. Major manual clock jumps affect wall-clock deadlines. Restoring old backups can discard recent reservations; wait for the longest cooldown and check equipment before resuming use.

The operator selector is attribution, not authentication or proof of identity. Hold-to-restart reduces accidental use, while the server independently enforces all permissions, membership, admission and cooldown checks. Recovery checks describe the server's observed DNS/internet connectivity, not the boot state of every powered device.
